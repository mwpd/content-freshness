How it is built →

Four small things, one question: is this post outdated?

Old tutorials keep ranking and getting shared long after they stop being right. A post counts as outdated when its last update is older than the limit you set. Publishing counts as the first update; any later save counts as a new one.

For readers

A notice on the post

A one-line paragraph at the top of outdated single posts. Pages, custom post types, archives and lists are left alone. It ships with the default style shown here; restyle it through .mwpd-content-freshness-notice, or dequeue the mwpd-content-freshness-notice style handle and bring your own.

For editors

A weekly digest

Editors and Administrators each get an email with up to 20 of the stalest posts, each linked to its editor. When nothing is stale, nothing is sent.

For editors

A “Last updated” column

In the Posts list, sortable, with outdated posts marked. Nothing to configure: it appears on the Posts screen and nowhere else.

For site owners

One setting

Under Settings › Reading: after how many days a post counts as outdated, from 1 to 36500. The default is 365.

Install, activate, done.

WordPress 6.0+, tested up to 7.1 PHP 7.4+ No account or external service MIT licence

  1. Download content-freshness.zip from the latest release.

  2. Upload it under Plugins › Add New › Upload Plugin and activate it.

  3. Optionally change the limit under Settings › Reading. The first digest goes out a week later.

# or, instead of steps 1 and 2, with WP-CLI
$ wp plugin install https://github.com/mwpd/content-freshness/releases/latest/download/content-freshness.zip --activate

Changing the notice

It comes with a default style. Override it through .mwpd-content-freshness-notice, or dequeue the mwpd-content-freshness-notice style handle. To change the markup, copy any template from the plugin’s views/ into content-freshness/views/ in your theme.

No digest arriving?

It’s sent by WP-Cron through wp_mail(). On quiet sites, add a real cron job; if no site email arrives, add an SMTP plugin.

On multisite

Activate it per site, or for the whole network: that sets the digest up in every site, and in sites created later. Each site keeps its own setting. Updating a network-active 1.0.0 to 1.0.1? Deactivate and activate it for the network once more.

Removing it

Deactivating keeps your setting. Deleting removes it and the weekly event, the only two things the plugin stores, from every site of a network.

How it is built

A simple plugin, built to show an approach.

Content Freshness is the worked example for the MWPD Basic Scaffold from Modern WordPress Plugin Development. The features are deliberately modest. They touch four different parts of WordPress, which makes them useful for showing how the scaffold keeps each part separate.

  • Runs onWordPress 6.0+, PHP 7.4+
  • Static analysisPHPStan level max, Psalm level 2
  • Tests in CIPHP 7.4 and 8.3, end-to-end on WordPress 6.0 and latest
  • Runtime dependenciesNone. No Composer packages, no build step
  • Every pushCI workflow
1

One feature, one service

The composition root lists the four services. None of them knows the others exist. The notice came first; each later feature was its own commit, adding a service and a line here without changing the ones before it.

2

Services say where and when, the scaffold does the rest

Each service implements small capability interfaces. A service that isn’t needed for a request is never constructed, and nothing branches on multisite: the scaffold visits each site for services that ask for it.

OutdatedPostNoticeSingle posts, once the query has runConditional · Delayed · Registerable
PostAgeColumnThe Posts list screen onlyConditional · Delayed · Registerable
FreshnessSettingAdmin requests; cleans up on uninstallDelayed · Registerable · SiteUninstallable
StaleContentDigestEvery request; schedules per siteRegisterable · SiteActivateable · SiteDeactivateable · SiteInitializable · SiteUninstallable
3

One rule, swappable

No feature reads the setting itself. They all ask a FreshnessPolicy interface. Bind your own class, for example to leave an evergreen category alone, and the notice, column and digest all follow it unchanged.

4

Rules a coding agent can follow

The architecture is written down and checked by tools, so a coding agent gets the same guidance as a person, and finds out right away when it strays.

AGENTS.md

The repository map, the commands, the design principles in short, and the hard rules.

Failures that explain

Architecture rules run in the tests and in PHPStan. Every failure says what to do instead.

The need before the workaround

Before reaching for a singleton or a global, an agent looks up the plugin’s way in docs/patterns.md.

No shortcuts to green

No lowered analysis levels, baselines or deleted tests. Claims are verified against the source, not memory.

Contributing

Unit, integration, architecture and end-to-end tests, plus PHPCS, PHPStan (level max) and Psalm. CI runs them on PHP 7.4 and 8.3, and the end-to-end suite on WordPress 6.0 and the latest release.
